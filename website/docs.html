Getting started

Installation

Three independent entry points. The CLI is the core — the daemon, reports, graph queries, chat, and dashboard all live there. The editor extensions are thin producers that talk to it.

CLI, via npm

Requires Node.js 22.5 or later and Git on your PATH.

npm install -g narrately
narrately onboard

VS Code extension

Search Narrately in the Extensions view, or install it from the CLI:

narrately install vscode
ext install narrately.narrately-collector # Marketplace alternative

JetBrains plugin

Settings → Plugins → Marketplace → search Narrately, or run narrately install intellij. One build works across IntelliJ IDEA, WebStorm, PyCharm, GoLand, and RubyMine — they share the platform SDK.

From source

The full source is available to clone, audit, or self-host — MIT licensed.

git clone https://github.com/narrately/narrately.github.io
cd narrately && npm install && npm link

Getting started

Onboarding wizard

narrately onboard asks a series of questions — the last one optional — and writes everything to ~/.narrately/config.yaml. Re-run it any time; it only asks about what's new.

  • Work profileConfirms software development — other profiles are recorded for the roadmap.
  • IDE detectionScans for installed VS Code and JetBrains IDEs and lets you pick which to collect from.
  • Collector installInstalls the extension or plugin for whatever you selected.
  • Shell integrationInstalls a history hook — command text and timestamp only, never output.
  • Project rootsAdd code directories, scan for repos, and label each for reports. Sets a default for code-change capture, then lets you override it per repo.
  • Privacy & retentionExclusions that are never recorded, whether captured diffs get secret-redaction, and an optional age-out window for old diffs.
  • Report preferencesLLM provider (with an optional model pin), manual vs. scheduled mode, verbosity, and optional email delivery.
  • Advanced (optional, skipped by default)Daemon port, minimum focus duration, and whether the git collector runs at all.

Anything the wizard doesn't ask, or that you want to change later without re-running it, is reachable directly — see Configuration file. Then give your main projects some context.

Getting started

Daily usage

Start the daemon once — it keeps running until you stop it or reboot.

narrately daemon start
narrately status

Then work normally. When you want a report:

narrately report # since your last report
narrately report --day 2026-07-28 # a specific day
narrately report --week # the current week, cross-project

Guides

Reports, Ask & Chat

Reports work without an API key — they just come out structured rather than narrated. Set ANTHROPIC_API_KEY or GEMINI_API_KEY for the written version.

narrately ask "what did I work on this week"
narrately chat # multi-turn, remembers the last few turns

Both are grounded in your recorded activity, your notes, and your project context — never raw file contents.

Guides

Ask & Chat, in more detail

narrately ask answers one question and exits. narrately chat opens a conversation that remembers context, so a follow-up like "what about last week?" resolves correctly. Both accept --provider and --model overrides for a single run.

Guides · new

Project context

Tracking only sees metadata — file names, durations, commit subjects. Give each project a short brief — what it is, what you're working towards, what its folders mean, its internal names — and the narrative, ask, and chat use it to explain the work in the project's own terms. src/billing/ becomes "the invoicing service".

narrately context # list projects and their context
narrately context edit api # write it in your editor, from a template
narrately context set api --link docs/ARCHITECTURE.md
narrately context set api --file brief.md
narrately context show api # exactly what the AI will see
  • Linked file--link re-reads the file on every report, so edits to your architecture doc flow in automatically.
  • Copied text--file, inline text, or context edit store a snapshot in the local database.
  • Zero setupDrop a .narrately.md in the project's root folder and it's picked up with no command. An explicit context set always wins over it.

The dashboard's Journal view has the same editor, with .md upload and drag-and-drop.

Only projects active in the report's period are included, capped at 6,000 characters each and 20,000 per prompt. The model is told to use it to interpret activity — never as evidence that work happened. Context stays local, is never synced to a team, and is sent to your LLM provider only alongside the activity it explains.

Web dashboard

A local app over the same data. The server binds to 127.0.0.1 only and ships its own fonts — it makes no outside requests.

narrately web
ViewWhat's there

Guides · new

Teams — Narrately Cloud

Optional and opt-in. Teammates' session metadata — project, start and end time, duration, languages, save and edit counts, lines added and removed — rolls up into one shared dashboard. The local tool keeps working exactly the same.

Team owner

narrately cloud signup # once, then confirm the email
narrately cloud login
narrately cloud create-org "Acme"
narrately cloud invite # prints a join code, valid 7 days
narrately cloud dashboard # open the team portal in your browser

Each teammate

narrately cloud signup
narrately cloud login
narrately cloud join <code>

While the daemon runs it syncs every 15 minutes. narrately sync pushes now, and narrately sync --days 30 re-sends a longer window. Turn auto-sync off with narrately config set cloud.auto_sync false. Owners can also invite and remove people from the team dashboard, and export the week as a CSV timesheet.

Never sent: file paths, diffs, commit messages, notes, project context, or any code. Those stay in ~/.narrately/narrately.db.
New teams get a 14-day trial. Afterwards, past rollups stay readable, but new syncs pause until the owner upgrades. Self-hosting setup (Supabase schema and Stripe billing) is in cloud/README.md.

Code change capture

Code change capture

Everything else tells you that something changed. This is the deliberate, opt-in exception that tells you what — off by default, at every layer.

Tier 1

Your commits

New commits get real diff text, redacted, scoped to the repo, never retroactive.

Tier 2

Uncommitted work

A diff on every save — the IDE only reads content once the daemon confirms opt-in.

Tier 3

Local retention

Raw text ages into a short summary after N days. No LLM involved, ever.

Code change capture

Tier 1 — your commits

Enable per project:

project_roots:
- path: C:/code/auth-service
label: auth-service
+ capture_diffs: true

Every file's diff is checked against your privacy exclusions, then redacted for secret-shaped strings before it ever touches disk:

function login() {
+ const apiKey = "[REDACTED:quoted-secret-assignment]";
return true;
}

Any single file's diff over 50KB is dropped entirely, not truncated — you get the line counts and a note, never a partial diff that reads as complete.

Code change capture

Tier 2 — uncommitted work

A second, independent switch — meaningfully more exposed, since it captures on every save before you've reviewed anything:

capture_diffs: true
+ capture_save_diffs: true

The IDE never reads a file's content speculatively — it asks the daemon first (GET /capture-config), and only reads & sends content for a project the daemon has actively confirmed opted in. The daemon re-checks independently before storing anything; the client's own gating is a courtesy, never the authority.

Code change capture

Tier 3 — local retention

Raw diff text is kept indefinitely by default. Set a retention window to age it out:

privacy:
+ diff_retention_days: 30

Past the window, a purely local, regex-based summarizer (no LLM, no API key required) replaces the raw text with a short description — "Added function login, processPayment; removed function oldAuth." The row stays; only the code itself is gone.

IDE collectors

VS Code collector

Plain JS, no build step, no dependencies. Tracks focus/save, edit volume, debug sessions, idle detection, diagnostics deltas, and file create/delete/rename. The Git branch is read directly from .git/HEAD — no dependency on the built-in Git extension being enabled.

IDE collectors

JetBrains plugin

Kotlin, built on the IntelliJ Platform Plugin template. Registered at project-startup time, not lazily, so files already open when the project loads still get captured. One build works across the whole family.

IDE collectors

Shell hook

Supports bash, zsh, fish, and PowerShell. Logs command text and timestamp only — never what a command printed, which is where secrets and output usually land.

Configuration file

Everything lives in ~/.narrately/config.yaml, written chmod 600 (a real restriction on macOS/Linux; NTFS doesn't enforce POSIX mode bits, so on Windows your account login is the actual boundary). Override the location with NARRATELY_HOME.

report:
mode: manual # or scheduled
verbosity: standard # brief | standard | detailed
provider: claude # or gemini
cloud:
auto_sync: true # team sync every 15 min while the daemon runs

Prefer not to hand-edit YAML? narrately config reads and writes the same file:

narrately config list # whole file, secrets redacted
narrately config get daemon.port
narrately config set report.verbosity detailed

Privacy model

Every line below is backed by code in the repository, not a policy document.

  • Local-firstNothing leaves the machine unless you explicitly enable email, an LLM narrative, or join a team.
  • Metadata only, by defaultFile paths, timestamps, commit subjects, integer counts — never file contents.
  • No command outputThe shell hook logs command text and timestamp — never what it printed.
  • Exclusions apply before storageExcluded paths, repos, and patterns never reach the database at all.
  • Loopback-only daemon and dashboardBound to 127.0.0.1, unauthenticated by design, never reachable off the machine.
  • Teams see session metadata onlyNarrately Cloud never receives paths, diffs, notes, project context, or code.
